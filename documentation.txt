================================================================================
1. PROJECT OVERVIEW
================================================================================

ReqBench is a Postman-like HTTP request testing tool built as a full-stack web
application. It lets users:

  - Build and send HTTP requests (GET, POST, PUT, PATCH, DELETE)
  - View responses with status, timing, headers, and formatted body
  - Manage multiple request tabs with full state persistence
  - Organize requests into collections with folders
  - Track request history (last 50 requests)
  - Use environment variables ({{variableName}}) across requests
  - Switch between environments (Development, Production, etc.)
  - Compare responses (JSON structural diff + line-based text diff)
  - Benchmark endpoints with concurrency, warmup, and detailed percentile stats
  - Generate code in cURL, JavaScript (fetch / axios), and Python (requests)
  - Import requests from cURL commands, Postman collections, and OpenAPI specs

Current persistence: all client data is stored in the browser's localStorage
through a repository abstraction. A Prisma + Neon Postgres schema is defined
and wired on the server (health check endpoint) for future cloud sync, but no
sync routes are called from the frontend yet.

4. HOW TO RUN
================================================================================

Prerequisites:
  - Node.js (v18+ for built-in fetch support)
  - npm

Start the backend:

    cd server
    npm install            (first time only)
    npx prisma generate    (first time only; generates Prisma client)
    npm run dev            (starts on http://localhost:3001)

Start the frontend:

    cd client
    npm install            (first time only)
    npm run dev            (starts on http://localhost:5173)

Open http://localhost:5173 in your browser.

The frontend dev server proxies /api/* requests to the backend, configured in
vite.config.ts using the VITE_SERVER_URL from client/.env.

Why a backend proxy?
  Browsers block cross-origin requests (CORS). The Express server performs
  the actual HTTP call server-side, so any URL works without CORS issues.

State persistence:
  Client state (tabs, history, collections, environments) is persisted in
  localStorage via Zustand's persist middleware and a repository layer that
  abstracts storage (so the local backend can later be replaced by a remote
  one without touching the stores).

6.4 REQUEST PROXY FLOW
-----------------------

  1. Validate that method and url are present (400 if missing)
  2. Validate URL format with new URL() (400 if invalid)
  3. Create AbortController with 30-second timeout
  4. Record start time with performance.now()
  5. Execute fetch() with method, headers, body, and abort signal
  6. Record response time
  7. Extract response headers into a plain object
  8. Read response body as text
  9. Return JSON with status, statusText, headers, body, responseTime

6.5 BENCHMARK RUNNER
--------------------

File: server/src/lib/benchmark.ts

Flow:
  1. Warmup phase: run N warmup requests sequentially; results discarded
  2. Create a shared counter and N concurrent worker functions
  3. Each worker pulls the next index, runs one request, stores the result,
     optionally sleeps delayMs, and loops until the counter reaches total
  4. When all workers finish, compute:
       - min / max / avg / median
       - p90 / p95 / p99 percentiles
       - requests per second (throughput)
       - statusCodeBreakdown (counts per status code, "error" for network fails)
       - timeSeries (ordered by request index — used by the frontend chart)

Each individual request uses an AbortController with the configured timeout
(default 30s) and fully consumes the response body so response time reflects
end-to-end latency.

6.6 ERROR HANDLING
------------------

  - Invalid URL:         new URL() throws -> 400
  - Network error:       caught -> 502 with error message
  - Timeout (>30s):      AbortController -> caught as AbortError -> 408
  - Backend unreachable: frontend catches fetch failure, shows a friendly
                         "Failed to reach backend server" message
  - DB disconnected:     /api/health/db returns 503 with Prisma error

7.2 STATE MANAGEMENT (ZUSTAND STORES)
--------------------------------------

All stores use Zustand. Two styles are used depending on whether the data
should survive a transient tab reload without being re-fetched:

  - useRequestStore uses the persist middleware directly (fully owned by the
    store; tab state is transient-ish and local to the browser)

  - useHistoryStore / useCollectionStore / useEnvironmentStore delegate
    reads and writes to a Repository (see section 7.3). Stores hold an
    in-memory copy and call repo methods to persist changes. This decoupling
    lets us swap local storage for a remote API without changing components.

Store: useRequestStore (localStorage key "reqbench-tabs")
  State:   tabs[], activeTabId
  Actions: addTab, removeTab, setActiveTab, updateTab, duplicateTab,
           sendRequest
  Notes:   Each tab also keeps a responseHistory[] (last 10 snapshots) used
           by the Compare feature.
           loading / error are stripped from persisted state.

Store: useHistoryStore (repository-backed)
  State:   entries[] (max 50, newest first)
  Actions: addEntry, removeEntry, clearAll

Store: useCollectionStore (repository-backed)
  State:   collections[] (each with folders[] and requests[])
  Actions: createCollection, renameCollection, deleteCollection,
           duplicateCollection, createFolder, renameFolder, deleteFolder,
           saveRequest, deleteRequest, duplicateRequest, importCollection

Store: useEnvironmentStore (repository-backed)
  State:   environments[], activeEnvironmentId
  Actions: createEnvironment, renameEnvironment, deleteEnvironment,
           setActiveEnvironment, updateVariables
  Default: "Development" environment with baseUrl=http://localhost:3001

7.3 REPOSITORY PATTERN
----------------------

Folder: client/src/repositories/

  - types.ts       Canonical shared types (HttpMethod, KeyValuePair, ResponseData,
                   SavedRequest, Collection, Environment, etc.)
  - interfaces.ts  HistoryRepository, CollectionsRepository,
                   EnvironmentsRepository interfaces (Promise-based)
  - local/*.ts     LocalStorage-backed implementations
  - index.ts       Exports default repo instances (currently the local ones)

The repository abstraction means:
  - Stores never touch localStorage directly
  - Swapping to a remote API is just a new implementation of the interface
  - All repo methods return Promises (even local ones) so signatures stay
    identical across backends

7.5 UTILITY LIBRARIES
---------------------

lib/resolveVariables.ts
  - resolveString(input, varMap)  -> { resolved, unresolved[] }
  - buildVariableMap(envVariables) -> Map<string, string>
  - findAllVariables(input)        -> string[] (extracts all {{var}} names)
  - collectUnresolved(texts[], map) -> string[] (all unresolved across texts)
  - Pattern: /\{\{(\w+)\}\}/g

lib/codegen.ts
  - Exports `generators`: cURL, JavaScript fetch, JavaScript axios,
    Python requests
  - Input: CodegenRequest { method, url, headers, body }
  - Each generator formats headers, body (pretty-JSON when possible),
    and handles simple-GET shortcut paths

lib/diff.ts
  - diffJson(left, right) -> recursive DiffEntry tree
    (added/removed/changed/unchanged/nested)
  - diffText(left, right) -> LineDiff[] using classical LCS dynamic programming
  - countDiffStats, hasDifferences, tryParseJson, formatValue helpers

lib/importers/curlParser.ts
  - Tokenizer that respects '...' / "..." quoting and \-line continuations
  - Recognizes: -X/--request, -H/--header, -d/--data/--data-raw/--data-binary,
    -u/--user, and common no-op flags (-s, -k, -L, -v, -i, --compressed)
  - Auto-detects Bearer / Basic from an Authorization header

lib/importers/postmanImporter.ts
  - Accepts Postman Collection v2.0 and v2.1 JSON
  - Converts folders (one level deep; deeper folders are flattened with a warning)
  - Handles: raw body, urlencoded body, formdata (best-effort JSON), auth
  - Emits ImportSummary { collectionName, requestCount, folderCount, warnings }

lib/importers/openApiImporter.ts
  - Accepts OpenAPI 3.x (JSON or YAML) and Swagger 2.0 (with a warning)
  - Built-in lightweight YAML parser for common OpenAPI shapes
  - Groups endpoints into folders by their first tag
  - Generates example request bodies from schemas (including $ref resolution
    inside #/components/schemas/ and allOf merging)
  - Depth-capped schema recursion (5 levels) to avoid infinite loops

8. FEATURE: REQUEST BUILDER & EXECUTION
================================================================================

8.1 BUILDING A REQUEST
----------------------

Users configure a request through the left panel:

  1. Select HTTP method (GET, POST, PUT, PATCH, DELETE) from dropdown
  2. Enter URL (supports {{variables}})
  3. Add query parameters in Params tab (key-value with enable/disable)
  4. Add headers in Headers tab (key-value with enable/disable)
  5. Enter request body in Body tab (JSON textarea)
  6. Configure auth in Auth tab:
     - None:   no auth headers
     - Bearer: adds Authorization: Bearer <token>
     - Basic:  adds Authorization: Basic <base64(input)>

8.2 SENDING A REQUEST
---------------------

When Send is clicked (or Ctrl+Enter pressed):

  1. Get active environment's variables, build variable map
  2. Scan ALL fields for {{var}} patterns (URL, params, headers, body, auth)
  3. If any unresolved variables found:
     -> BLOCK the request
     -> Show error: "Unresolved variables: {{var1}}, {{var2}}..."
     -> Never silently replace with empty string
  4. If all variables resolve:
     -> Replace {{var}} with values in all fields
     -> Build full URL with resolved query params
     -> Build headers object with resolved values + auth header
     -> POST to /api/requests/execute with resolved data
  5. Backend proxies the request to the external API
  6. Response is displayed in the right panel
  7. A new ResponseSnapshot is prepended to the tab's responseHistory[]
     (capped at 10) for later comparison
  8. History entry is recorded (method, url, status, time, timestamp)

8.3 VIEWING THE RESPONSE
-------------------------

Right panel shows:
  - Status: color-coded (green <300, yellow <400, red >=400)
  - Time: response time in milliseconds
  - Size: response body size in B or KB
  - Body tab: pretty-printed JSON (or raw text if not valid JSON)
  - Headers tab: key-value list of response headers
  - Compare button: opens CompareModal when 2+ snapshots exist

Error states:
  - Loading: spinner animation
  - Error:   red banner with error message
  - Empty:   "Send a request to see the response" + "Ctrl+Enter to send"

8.4 KEYBOARD SHORTCUTS
-----------------------

  Ctrl+Enter (or Cmd+Enter on Mac): Send the current request

9.3 TAB NAME DERIVATION
------------------------

  Tab names auto-update based on the URL:
    - Empty URL:   "New Request"
    - Valid URL:   host + path (e.g., "api.example.com/users")
    - Invalid URL: first 30 chars of input

  When closing a tab, the neighbor at the same position is selected

10.1 HOW HISTORY IS RECORDED
-----------------------------

  Recording is done by calling useHistoryStore.getState().addEntry() from

10.3 STORAGE LIMITS

  - Maximum 50 entries (newest first, oldest trimmed)
  - localStorage key: "reqbench-history"
  - Persists across page refreshes

12. FEATURE: ENVIRONMENT VARIABLES
================================================================================

12.1 ENVIRONMENT STRUCTURE
---------------------------

  Environment
    |-- id: string (UUID)
    |-- name: string
    |-- variables: EnvVariable[]
        |-- key: string
        |-- value: string
        |-- secret: boolean          (hides value in UI when true)
        |-- enabled: boolean         (disabled variables are skipped)

  Default environment on first load:
    Name: "Development"
    Variables: baseUrl = http://localhost:3001

12.2 VARIABLE SYNTAX
---------------------

  Use {{variableName}} anywhere in:
    - URL field
    - Query parameter keys and values
    - Header keys and values
    - Request body
    - Auth token field

  Examples:
    {{baseUrl}}/api/users
    Authorization: Bearer {{apiKey}}
    {"userId": "{{userId}}"}

  Pattern: /\{\{(\w+)\}\}/g — names must be [a-zA-Z0-9_]

12.3 RESOLUTION FLOW
---------------------

  1. User types raw request with {{variables}}
  2. UI shows live resolved preview below URL bar
  3. On Send:
     a. Get active environment's variables
     b. Build Map<string, string> from enabled variables
     c. Scan ALL fields for {{var}}
     d. If any variable is not in the map -> BLOCK with error
     e. Otherwise -> replace {{var}} with values and send

  Variables are resolved at SEND TIME. The raw {{var}} syntax is always
  preserved in the tab's stored state.

12.4 UNRESOLVED VARIABLE HANDLING
----------------------------------

  Unresolved variables are NEVER silently replaced with empty strings.

  In the UI:
    - Yellow warning below URL bar: "Unresolved: {{varName}}"
    - Shows while typing (live feedback)

  On Send:
    - Request is BLOCKED
    - Error displayed: "Unresolved variables: {{var1}}, {{var2}}.
      Define them in the active environment or remove them."

12.5 SECRET VARIABLES
----------------------

  Variables can be marked "secret" in the Environment Manager.
  - Value field becomes type="password" (dots instead of text)
  - Resolves identically at send time
  - Purpose: hide sensitive values (tokens, API keys) on screen

12.6 ENVIRONMENT MANAGER
--------------------------

  Opened via the gear icon next to the environment dropdown.

  Features:
    - List of all environments with expand/collapse
    - Green dot: click to set active (click again to deactivate)
    - "active" label next to the active environment
    - Variable editor per env (checkbox, key, value, secret, delete, add)
    - Inline rename for environment names
    - "+ New Environment" button
    - Help text at bottom explaining {{var}} syntax

13. FEATURE: RESPONSE COMPARISON / DIFF
================================================================================

13.1 RESPONSE SNAPSHOT HISTORY
-------------------------------

  Every successful sendRequest() stores a ResponseSnapshot in the tab:
    - id (UUID)
    - response (the full ResponseData)
    - timestamp
    - label, e.g. "GET 200 - 14:32:05"

  The tab keeps the most recent 10 snapshots (MAX_RESPONSE_HISTORY = 10).

13.2 COMPARE MODAL
-------------------

  Triggered by the Compare button in ResponseViewer (enabled when 2+ snapshots
  exist).

  Workflow:
    1. Pick "left" and "right" snapshots from two dropdowns
    2. Choose mode: JSON Diff or Text Diff
    3. Review results; summary shows counts of added/removed/changed/unchanged

13.3 JSON STRUCTURAL DIFF
--------------------------

  File: client/src/lib/diff.ts -> diffJson()

  Produces a recursive tree of DiffEntry nodes:
    - added     (key exists only on the right)
    - removed   (key exists only on the left)
    - changed   (values differ — scalar or array)
    - nested    (object recursed into — children carry the actual diffs)
    - unchanged (values identical)

  Arrays are compared by full JSON.stringify (any difference -> changed).

13.4 TEXT LINE DIFF (LCS)
-------------------------

  File: client/src/lib/diff.ts -> diffText()

  Classic Longest Common Subsequence dynamic-programming approach:
    - Build dp[m+1][n+1] with lengths of common subsequences
    - Backtrack to produce LineDiff[] with type same/added/removed and
      left/right line numbers
  Used by CompareModal for the line-by-line view.

14. FEATURE: BENCHMARKING
================================================================================

14.1 BENCHMARK CONFIGURATION
-----------------------------

  User inputs (BenchmarkModal):
    - totalRequests: number of iterations (1..1000)
    - concurrency:   parallel workers (1..50)
    - warmupCount:   discarded warmup requests (0..10)
    - delayMs:       sleep between requests per worker (0..5000)

  The UI reuses the current tab's resolved method, URL, headers, and body
  (after variable substitution).

14.2 WORKER POOL EXECUTION
---------------------------

  See server/src/lib/benchmark.ts -> runBenchmark():
    1. Run `warmupCount` warmup requests sequentially (results discarded)
    2. Start `concurrency` workers that each:
         - Claim the next index from a shared counter
         - Call fetch + consume response body (so responseTime is accurate)
         - Record status, responseTime, timestamp (or error)
         - Optionally sleep delayMs
         - Loop until counter reaches total
    3. await Promise.all(workers), measure totalDuration

14.3 STATISTICS CALCULATED
---------------------------

  Aggregated output:
    - totalRequests, successCount (<500), failureCount, errorRate (%)
    - totalDuration (ms), requestsPerSecond
    - minResponseTime, maxResponseTime, avgResponseTime
    - medianResponseTime, p90, p95, p99 percentiles
    - statusCodeBreakdown: { "200": 98, "500": 2, "error": 1 }
    - timeSeries: [{ index, responseTime, status }, ...]

14.4 BENCHMARK MODAL UI
------------------------

  - Config form at top (inputs above)
  - Run button -> shows loading spinner, POSTs /api/benchmarks/run
  - Results panel:
      - Summary cards (RPS, median, p95, error rate, etc.)
      - Status code breakdown chips
      - Time-series mini-chart (response time per request index)

15. FEATURE: CODE GENERATION
================================================================================

15.1 SUPPORTED GENERATORS
--------------------------

  Registered in client/src/lib/codegen.ts:

    id      | Label                 | Language
    --------+-----------------------+-----------
    curl    | cURL                  | bash
    fetch   | JavaScript (fetch)    | javascript
    axios   | JavaScript (axios)    | javascript
    python  | Python (requests)     | python

  Each generator receives:
    { method, url (with ?query=params appended), headers, body }

  Output conventions:
    - cURL wraps values in single quotes, escapes embedded "'" as '\''
    - fetch/axios pretty-print JSON bodies inside JSON.stringify({...})
    - Python renders JSON bodies as a native dict and uses json=payload;
      non-JSON bodies become a triple-quoted string with data=payload

15.2 RESOLUTION BEFORE GENERATION
----------------------------------

  CodeGenModal builds a resolved request before invoking the generator:
    - Applies the active environment's {{variables}}
    - Appends enabled query params to the URL
    - Produces headers object including auth (bearer / basic b64)
  Unresolved variables remain as literal {{name}} in the output, and the
  modal footer reminds the user which environment (if any) was used.

15.3 CODE GEN MODAL UI
-----------------------

  - Language tabs (scrollable if needed)
  - Pre-formatted code area (whitespace preserved, wraps long lines)
  - Copy-to-clipboard button with a 2-second "Copied" confirmation

16. FEATURE: IMPORT (cURL, POSTMAN, OPENAPI)
================================================================================

16.1 IMPORT MODAL
------------------

  Opened via the Import button in the URL bar.

  Three tabs inside:
    - cURL     -> paste textarea, target-tab selector
    - Postman  -> file picker (.json)
    - OpenAPI  -> file picker (.json / .yaml / .yml)

  Errors appear as a red banner; successful imports (Postman/OpenAPI) show
  a green summary with counts and a warnings list.

16.2 cURL IMPORT
----------------

  Parser: client/src/lib/importers/curlParser.ts

  Supported:
    - -X / --request <METHOD>
    - -H / --header "Key: Value"
    - -d / --data / --data-raw / --data-binary <body>
    - -u / --user <user:password>      (becomes Basic Auth)
    - Bearer / Basic auto-detected from an Authorization: header
    - '...' and "..." quoting, backslash escapes, \-newline continuations
    - Ignores common no-op flags: -s, -k, -L, -v, -i, --compressed

  Not supported (tracked as limitations):
    - -F / --form multipart / file uploads
    - -b / --cookie cookies
    - --url as a flag (URL must be positional)
    - Proxy flags (-x, --proxy)

  UI:
    - Radio: "Fill current tab" (default) or "Open in new tab"
    - Clear, specific parse errors ("Unsupported HTTP method", "No URL found",
      "Invalid header format", etc.)

16.3 POSTMAN COLLECTION IMPORT
-------------------------------

  Parser: client/src/lib/importers/postmanImporter.ts

  Supports Postman Collection v2.0 and v2.1 JSON exports.

  Conversion:
    - Top-level `item[]` with sub-`item[]` -> folders
    - Deeper nested folders are flattened into the parent with a warning
    - Raw, url-encoded, form-data bodies (form-data is JSON-ified best-effort)
    - Bearer / Basic auth from request.auth
    - Query params (including disabled)
    - Disabled headers and params preserved with enabled=false

  Unsupported / warns:
    - Body modes file / graphql produce warnings
    - Pre-request scripts and tests are ignored
    - Unsupported HTTP methods produce a skip warning

  Output: appends a new Collection via collectionsRepo.importCollection().

16.4 OPENAPI SPEC IMPORT
-------------------------

  Parser: client/src/lib/importers/openApiImporter.ts

  Accepts OpenAPI 3.x JSON or YAML (and Swagger 2.0 with a warning).

  Conversion:
    - title -> collection name
    - servers[0].url -> base URL prefix
    - Operations grouped into folders by their first tag
      (untagged operations go to the collection's root requests)
    - Generates a sample request body from:
        * content["application/json"].example
        * content["application/json"].examples (first entry)
        * schema -> recursive example from type/default/enum/allOf/oneOf/anyOf
    - Resolves $ref for #/components/schemas/* (depth-capped at 5)
    - Path parameters replaced with example values in the URL
    - Query and header parameters materialized into the Params/Headers tabs

  Limitations:
    - Lightweight built-in YAML parser: no anchors/aliases, limited flow syntax
    - Security schemes detected but not auto-applied
    - Only JSON request bodies are auto-generated (other content types warned)

  Output: appends a new Collection via collectionsRepo.importCollection().

21. TESTING GUIDE
================================================================================

HEALTH CHECK:
  1. cd server && npm run dev
  2. curl http://localhost:3001/api/health          -> {"status":"ok"}
  3. curl http://localhost:3001/api/health/db       -> confirms DB connection

GET REQUEST:
  1. Start both servers
  2. Open http://localhost:5173
  3. URL: https://jsonplaceholder.typicode.com/todos/1
  4. Click Send (or Ctrl+Enter)
  5. Right panel: 200 OK, response time, JSON body

POST REQUEST:
  1. Method = POST
  2. URL: https://jsonplaceholder.typicode.com/posts
  3. Headers: add Content-Type = application/json
  4. Body: {"title": "test", "body": "hello", "userId": 1}
  5. Send -> 201 Created

TABS:
  1. "+" to add tabs, fill different URLs
  2. Switch between tabs — each preserves its own state
  3. Hover a tab: duplicate and close buttons
  4. Refresh the page: all tabs restore

HISTORY:
  1. Send a few requests
  2. Click History in Navbar, search, open an entry, delete an entry

COLLECTIONS:
  1. Fill a request, click Save, create a new collection
  2. Open Collections panel; click the saved request to reopen in a new tab
  3. Add folders, rename, duplicate, delete

ENVIRONMENT VARIABLES:
  1. Gear icon next to env dropdown: "Development" has baseUrl
  2. URL: {{baseUrl}}/api/health — preview resolves live
  3. Send -> {"status":"ok"}
  4. Create "Production" with baseUrl=https://jsonplaceholder.typicode.com
  5. Switch envs: preview updates, Send hits the new host

UNRESOLVED VARIABLES:
  1. Type {{baseUrl}}/users/{{userId}} without defining userId
  2. Yellow warning appears; Send is BLOCKED with an error

COMPARE / DIFF:
  1. Send the same request twice (vary something between runs if you can)
  2. Click Compare in ResponseViewer
  3. Pick two snapshots, toggle JSON / Text modes

BENCHMARK:
  1. Click the Bench button in the URL bar
  2. Set total=50, concurrency=5, warmup=2
  3. Run; inspect RPS, p95, status breakdown, time series

CODE GENERATION:
  1. Configure a request with params/headers/body
  2. Click </> in the URL bar
  3. Cycle cURL / fetch / axios / Python tabs; verify all fields are reflected
  4. Click Copy; paste the snippet into its runtime and confirm it sends
     the same request

cURL IMPORT:
  1. Click Import -> cURL tab
  2. Paste:
       curl -X POST 'https://jsonplaceholder.typicode.com/posts?userId=1' \
         -H 'Content-Type: application/json' \
         -H 'Authorization: Bearer abc123' \
         -d '{"title":"hello","body":"world"}'
  3. Leave "Fill current tab" selected, click Import
  4. Verify method, URL (with query), header, bearer auth, body all populated
  5. Send -> 201 Created
  6. Paste garbage text to confirm the error banner renders

POSTMAN IMPORT:
  1. Import -> Postman tab
  2. Select a Postman Collection v2.1 JSON export
  3. Green summary appears with counts + any warnings
  4. Open Collections panel; folder/request tree matches

OPENAPI IMPORT:
  1. Import -> OpenAPI tab
  2. Select a spec file (e.g. petstore OpenAPI 3 JSON or YAML)
  3. Green summary shows folders per tag + endpoint count
  4. Open a generated request; verify example body and path params

PERSISTENCE:
  1. Set up tabs, collections, history, environments
  2. Hard refresh (F5); everything restores
  3. Inspect DevTools > Application > Local Storage to see raw data
