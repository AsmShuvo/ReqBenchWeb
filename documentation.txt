1. PROJECT OVERVIEW
================================================================================

ReqBench is a Postman-like HTTP request testing tool built as a full-stack web
application. It allows users to:

  - Build and send HTTP requests (GET, POST, PUT, PATCH, DELETE)
  - View responses with status, timing, headers, and formatted body
  - Manage multiple request tabs with full state persistence
  - Organize requests into collections with folders
  - Track request history (last 50 requests)
  - Use environment variables ({{variableName}}) across requests
  - Switch between environments (Development, Production, etc.)

All data is stored locally in the browser's localStorage. No database is
connected yet. The backend serves only as a proxy to execute HTTP requests
(avoiding CORS restrictions).

4. HOW TO RUN
================================================================================

Prerequisites:
  - Node.js (v18+ for built-in fetch support)
  - npm

Start the backend:

    cd server
    npm install          (first time only)
    npm run dev          (starts on http://localhost:3001)

Start the frontend:

    cd client
    npm install          (first time only)
    npm run dev          (starts on http://localhost:5173)

Open http://localhost:5173 in your browser.

The frontend dev server proxies /api/* requests to the backend (configured in
vite.config.ts using the VITE_SERVER_URL from client/.env).

5. ARCHITECTURE OVERVIEW
================================================================================

    Browser (localhost:5173)
        |
        |  User builds request in UI
        |  (method, URL with {{vars}}, headers, body, auth)
        |
        v
    React Frontend (Zustand stores)
        |
        |  1. Resolves {{variables}} from active environment
        |  2. Checks for unresolved variables (blocks if any)
        |  3. Sends POST /api/requests/execute to backend
        |
        v
    Vite Dev Proxy (/api/* -> localhost:3001)
        |
        v
    Express Backend (localhost:3001)
        |
        |  POST /api/requests/execute
        |  1. Validates URL
        |  2. Calls fetch() to external API (server-side, no CORS issues)
        |  3. Measures response time
        |  4. Returns { status, statusText, headers, body, responseTime }
        |
        v
    External API (e.g., jsonplaceholder.typicode.com)

Why a backend proxy?
  Browsers block cross-origin requests (CORS). The Express server makes the
  actual HTTP call server-side, so any URL works without CORS issues.

State persistence:
  All client state (tabs, history, collections, environments) is persisted
  in localStorage using Zustand's persist middleware. No server-side storage
  is used yet.

6.1 EXPRESS SERVER SETUP
------------------------

File: server/src/index.ts

  - Express 5 with CORS enabled and JSON body parsing
  - Runs on port 3001
  - Dev script: "tsx watch src/index.ts" (auto-restarts on file changes)

6.2 API ENDPOINTS
-----------------

GET /api/health
  Response: { "status": "ok" }
  Purpose:  Health check to verify backend is running

POST /api/requests/execute
  Request body:
    {
      "method": "GET" | "POST" | "PUT" | "PATCH" | "DELETE",
      "url": "https://example.com/api/resource",
      "headers": { "Content-Type": "application/json", ... },
      "body": "..." (optional, ignored for GET/HEAD)
    }

  Success response:
    {
      "status": 200,
      "statusText": "OK",
      "headers": { "content-type": "application/json", ... },
      "body": "...",
      "responseTime": 142
    }

  Error responses:
    400: { "error": "method and url are required" }
    400: { "error": "Invalid URL" }
    408: { "error": "Request timed out (30s)" }
    502: { "error": "Network error: <message>" }

6.3 REQUEST PROXY FLOW
-----------------------

  1. Validate that method and url are present (400 if missing)
  2. Validate URL format with new URL() (400 if invalid)
  3. Create AbortController with 30-second timeout
  4. Record start time with performance.now()
  5. Execute fetch() with method, headers, body, and abort signal
  6. Record response time
  7. Extract response headers into a plain object
  8. Read response body as text
  9. Return JSON with status, statusText, headers, body, responseTime

6.4 ERROR HANDLING
------------------

  - Invalid URL:        Caught by new URL() constructor, returns 400
  - Network error:      Caught in try/catch, returns 502 with error message
  - Timeout (>30s):     AbortController fires, caught as AbortError, returns 408
  - Backend unreachable: Frontend catches fetch failure: "Failed to reach backend server"

8. FEATURE: REQUEST BUILDER & EXECUTION
================================================================================

8.1 BUILDING A REQUEST
----------------------

Users configure a request through the left panel:

  1. Select HTTP method (GET, POST, PUT, PATCH, DELETE) from dropdown
  2. Enter URL (supports {{variables}})
  3. Add query parameters in Params tab (key-value with enable/disable)
  4. Add headers in Headers tab (key-value with enable/disable)
  5. Enter request body in Body tab (JSON textarea)
  6. Configure auth in Auth tab:
     - None: no auth headers
     - Bearer Token: adds Authorization: Bearer <token>
     - Basic Auth: adds Authorization: Basic <base64(input)>

8.2 SENDING A REQUEST
---------------------

When Send is clicked (or Ctrl+Enter pressed):

  1. Get active environment's variables, build variable map
  2. Scan ALL fields for {{var}} patterns (URL, params, headers, body, auth)
  3. If any unresolved variables found:
     -> BLOCK the request
     -> Show error: "Unresolved variables: {{var1}}, {{var2}}..."
     -> Never silently replace with empty string
  4. If all variables resolve:
     -> Replace {{var}} with values in all fields
     -> Build full URL with resolved query params
     -> Build headers object with resolved values + auth header
     -> POST to /api/requests/execute with resolved data
  5. Backend proxies the request to the external API
  6. Response is displayed in the right panel
  7. History entry is recorded (method, url, status, time, timestamp)

8.3 VIEWING THE RESPONSE
-------------------------

Right panel shows:
  - Status: color-coded (green <300, yellow <400, red >=400)
  - Time: response time in milliseconds
  - Size: response body size in B or KB
  - Body tab: pretty-printed JSON (or raw text if not valid JSON)
  - Headers tab: key-value list of response headers

Error states:
  - Loading: spinner animation
  - Error: red banner with error message
  - Empty: "Send a request to see the response" + "Ctrl+Enter to send"

8.4 KEYBOARD SHORTCUTS
-----------------------

  Ctrl+Enter (or Cmd+Enter on Mac): Send the current request

  When closing a tab, the neighbor at the same position is selected
  (or the last tab if closing the rightmost).

10. FEATURE: REQUEST HISTORY
================================================================================

10.1 HOW HISTORY IS RECORDED
-----------------------------

  After every sendRequest() call (success or error), an entry is added:
    - method: HTTP method used
    - url: full resolved URL (after variable substitution)
    - status: HTTP status code (null if network error)
    - responseTime: milliseconds (null if network error)
    - timestamp: Date.now() when request was made

  Recording is done by calling useHistoryStore.getState().addEntry()
  directly from the request store (cross-store communication).

10.2 HISTORY PANEL
------------------

  - Opens as a slide-over from the right (triggered by History button in Navbar)
  - Search input filters by URL, method, or status code
  - Each entry shows: method badge, truncated URL, status, time, relative timestamp
  - Click an entry: creates new tab with that method + URL, closes panel
  - Hover an entry: reveals delete button
  - "Clear all" button in header
  - Footer shows: "X / 50 requests stored"

10.3 STORAGE LIMITS
--------------------

  - Maximum 50 entries (newest first, oldest trimmed)
  - localStorage key: "reqbench-history"
  - Persists across page refreshes

12. FEATURE: ENVIRONMENT VARIABLES
================================================================================

12.1 ENVIRONMENT STRUCTURE
---------------------------

  Environment
    |-- id: string (UUID)
    |-- name: string ("Development", "Production", etc.)
    |-- variables: EnvVariable[]
        |-- key: string ("baseUrl", "apiKey", etc.)
        |-- value: string ("http://localhost:3001", "sk-...", etc.)
        |-- secret: boolean (hides value in UI when true)
        |-- enabled: boolean (disabled variables are skipped during resolution)

  Default environment on first load:
    Name: "Development"
    Variables: baseUrl = http://localhost:3001

12.2 VARIABLE SYNTAX
---------------------

  Use {{variableName}} anywhere in:
    - URL field
    - Query parameter keys and values
    - Header keys and values
    - Request body
    - Auth token field

  Examples:
    {{baseUrl}}/api/users
    Authorization: Bearer {{apiKey}}
    {"userId": "{{userId}}"}

  Pattern: /\{\{(\w+)\}\}/g
  Variable names must be word characters: [a-zA-Z0-9_]

12.3 RESOLUTION FLOW
---------------------

  1. User types raw request with {{variables}}
  2. UI shows live resolved preview below URL bar
  3. On Send:
     a. Get active environment's variables
     b. Build Map<string, string> from enabled variables
     c. Scan ALL fields (URL, params, headers, body, auth) for {{var}}
     d. If any variable is not in the map -> BLOCK request with error
     e. If all resolve -> replace {{var}} with values, then send

  Variables are resolved at SEND TIME, not at edit time. The raw {{var}}
  syntax is always preserved in the tab's stored state.

12.4 UNRESOLVED VARIABLE HANDLING
----------------------------------

  Unresolved variables are NEVER silently replaced with empty strings.

  In the UI:
    - Yellow warning below URL bar: "Unresolved: {{varName}}"
    - Shows while typing (live feedback)

  On Send:
    - Request is BLOCKED
    - Error displayed: "Unresolved variables: {{var1}}, {{var2}}.
      Define them in the active environment or remove them."

  To fix:
    - Add the variable to the active environment, or
    - Switch to an environment that has it, or
    - Remove the {{var}} from the request

12.5 SECRET VARIABLES
----------------------

  Variables can be marked as "secret" in the Environment Manager.
  - Value field uses type="password" (shows dots instead of text)
  - Functionally identical: resolves the same way at send time
  - Purpose: hide sensitive values (API keys, tokens) from shoulder-surfing

12.6 ENVIRONMENT MANAGER
--------------------------

  Opened via the gear icon next to the environment dropdown in Navbar.

  Features:
    - List of all environments with expand/collapse
    - Green dot: click to set as active (click again to deactivate)
    - "active" label shown next to the active environment
    - Variable editor per environment:
      - Checkbox (enable/disable)
      - Key input (monospace)
      - Value input (text or password based on secret flag)
      - Secret checkbox
      - Delete button
      - "+ Add variable" button
    - Inline rename for environment names
    - "+ New Environment" button
    - Help text at bottom explaining {{var}} syntax

16. TESTING GUIDE
================================================================================

TESTING THE HEALTH CHECK:
  1. Start backend: cd server && npm run dev
  2. curl http://localhost:3001/api/health
  3. Expected: {"status":"ok"}

TESTING A GET REQUEST:
  1. Start both servers
  2. Open http://localhost:5173
  3. Enter URL: https://jsonplaceholder.typicode.com/todos/1
  4. Click Send (or Ctrl+Enter)
  5. Right panel shows: 200 OK, response time, JSON body

TESTING A POST REQUEST:
  1. Change method to POST
  2. URL: https://jsonplaceholder.typicode.com/posts
  3. Headers tab: add Content-Type = application/json
  4. Body tab: {"title": "test", "body": "hello", "userId": 1}
  5. Click Send
  6. Right panel shows: 201 Created

TESTING TABS:
  1. Click "+" to add tabs
  2. Fill different URLs in each tab
  3. Switch between tabs - each preserves its own state
  4. Hover a tab to see duplicate and close buttons
  5. Refresh the page - all tabs restore

TESTING HISTORY:
  1. Send a few requests
  2. Click "History" in navbar
  3. Search by URL, method, or status code
  4. Click an entry to reopen it in a new tab
  5. Hover entries to delete individually

TESTING COLLECTIONS:
  1. Fill in a request with URL, headers, body
  2. Click "Save" next to Send
  3. Create a new collection, give it a name, click Save
  4. Click "Collections" in navbar
  5. Expand the collection, click the saved request to reopen it
  6. Hover items for rename, duplicate, delete actions
  7. Add folders inside collections for organization

TESTING ENVIRONMENT VARIABLES:
  1. Click the gear icon next to the environment dropdown
  2. The "Development" env should exist with baseUrl = http://localhost:3001
  3. Close the manager
